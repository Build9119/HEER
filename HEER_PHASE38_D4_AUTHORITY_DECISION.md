## 1. CANONICAL IDENTITIES

### tenant_scope

| Property | Definition |
|----------|-----------|
| **Meaning** | An isolation boundary identifier. Every business belongs to exactly one tenant. Every worker is registered to serve one or more tenants. The tenant is the unit of platform-level isolation. |
| **Authority owner** | Business Registry — the sole source of truth for which tenant a business belongs to. |
| **Lifecycle owner** | Business Registry — created when a business is added; immutable without Architecture Owner approval. |
| **Persistence owner** | Business Registry (businesses.json or equivalent configuration store). NOT persisted by D1Persistence. |
| **May be derived from another identity?** | NO. `tenant_scope` is an independent, authoritative classification. It must NOT be derived from `business_id`, `worker_id`, or any other identity. The current conflation of `business_id` as `tenant_scope` is an architectural defect. |

### business_id

| Property | Definition |
|----------|-----------|
| **Meaning** | A unique identifier for a business entity. A business is the unit of work-scope: it owns data, vaults, and intelligence. Multiple businesses may share a tenant. |
| **Authority owner** | Business Registry (businesses.json). |
| **Lifecycle owner** | Business Registry — created on business addition; disabled/enabled by admin. |
| **Persistence owner** | Business Registry. NOT persisted by D1Persistence. |
| **May be derived from another identity?** | NO. `business_id` is an independent identity. It must NOT be used as `tenant_scope` (current defect). |

### worker_id

| Property | Definition |
|----------|-----------|
| **Meaning** | A unique, immutable identifier for a worker process. Assigned at worker creation; never changes for the lifetime of the worker definition. |
| **Authority owner** | WorkerRegistry — validates uniqueness and epoch constraints. |
| **Lifecycle owner** | WorkerRegistry — registered on spawn; superseded on new instance+epoch; terminal on DEPARTED. |
| **Persistence owner** | D1Persistence (if enabled); WorkerRegistry (in-memory). |
| **May be derived from another identity?** | NO. `worker_id` is independently assigned. |

### worker_instance_id

| Property | Definition |
|----------|-----------|
| **Meaning** | A unique identifier for a specific process instance of a worker. Changes on every restart/spawn. |
| **Authority owner** | WorkerRegistry — validated against stored instance during heartbeat/depart. |
| **Lifecycle owner** | Created fresh on each worker spawn; does not persist across restarts. |
| **Persistence owner** | D1Persistence (if enabled); WorkerRegistry (in-memory). |
| **May be derived from another identity?** | NO. Must be a fresh unique value per spawn. |

### worker_epoch

| Property | Definition |
|----------|-----------|
| **Meaning** | A monotonically increasing integer fencing signal. Prevents stale worker identity from being used after a restart. New instance MUST have epoch > current. |
| **Authority owner** | WorkerRegistry — sole authority for epoch generation, validation, and stale rejection (D3 GREEN). |
| **Lifecycle owner** | WorkerRegistry — incremented on each new instance registration; immutable per registration. |
| **Persistence owner** | D1Persistence (if enabled); WorkerRegistry (in-memory). |
| **May be derived from another identity?** | NO. Generated by WorkerRegistry per D3 invariants. |

## 2. AUTHORITATIVE RELATIONSHIPS

### business_id → tenant_scope

| Property | Decision |
|----------|---------|
| **Where it lives** | **Business Registry** — each business definition gains a `tenant_scope` field. |
| **Type** | Configuration-derived. A business is assigned to a tenant at registration time. |
| **Should it be persisted?** | YES — it is part of the business definition (businesses.json). It is NOT a runtime authorization table; it is configuration. |
| **Should it be registry-derived?** | NO — it is not derived from runtime registry state. It is an explicit declaration. |
| **Should it be part of WorkerIdentity?** | NO — WorkerIdentity describes the worker, not the business-to-tenant mapping. |
| **Should it be transient?** | NO — it is a stable configuration property of the business. |

**Canonical form:**

```json
{
  "id": "business_a",
  "name": "Business A",
  "tenant_scope": "tenant_a",
  "authorized_workers": ["worker_alpha"],
  ...
}
```

### worker → authorized_business(es)

| Property | Decision |
|----------|---------|
| **Where it lives** | **Business Registry** — each business declares which workers are authorized to execute its tasks. This is a business-centric authorization model. |
| **Type** | Configuration-derived. Explicit whitelist per business. |
| **Should it be persisted?** | YES — part of business definition. NOT part of D1Persistence. |
| **Should it be registry-derived?** | NO — it is an explicit authorization declaration, not derived from runtime state. |
| **Should it be part of WorkerIdentity?** | **NO.** WorkerIdentity is immutable per registration. Adding `authorized_businesses` to WorkerIdentity would couple business authorization to worker lifecycle, which is wrong — a business can authorize a worker without the worker knowing about it. |
| **Should it be transient?** | NO — it is a stable authorization policy. |

**Rationale for business-centric (not worker-centric):**

- The **business owner** decides which workers may execute its tasks. This is the correct authority direction.
- A worker does not need to "know" which businesses it serves; it only needs to present its identity. The authorization check is: "is this worker on the business's authorized list?"
- This avoids the need for a separate authorization table, avoids modifying WorkerIdentity, and avoids modifying D1 persistence.
- If the relationship were worker-centric (`worker_id → [business_ids]`), it would require either modifying WorkerIdentity or creating a new persistence table, and the worker would need to declare its authorization at registration — which is self-claimed and untrustworthy.

## 3. ARCHITECTURE OPTIONS EVALUATION

### Option A: Business Registry owns business_id → tenant_scope

| Dimension | Assessment |
|-----------|-----------|
| Authority duplication | **NONE.** Single source: Business Registry. |
| D1 boundary impact | **NONE.** D1Persistence stores worker identity; Business Registry is separate. |
| D3 impact | **NONE.** Epoch authority is unchanged. |
| Persistence impact | **NONE.** Business definition already persisted in businesses.json. Adding `tenant_scope` and `authorized_workers` to the JSON schema. |
| Security strength | **MODERATE-HIGH.** Explicit tenant mapping + explicit worker whitelist provides true business-level isolation. |
| Same-tenant isolation | **YES.** Business A and Business B under same tenant have independent `authorized_workers` lists. |
| Operational complexity | **LOW.** Single configuration change. No new tables, no new services. |
| Compatibility with frozen contracts | **FULL.** No changes to worker_contracts.py, worker_registry.py, d1_persistence.py, execution_engine.py. |

### Option B: Worker registration owns authorized_businesses

| Dimension | Assessment |
|-----------|-----------|
| Authority duplication | **POTENTIAL.** If WorkerIdentity carries authorized_businesses AND Business Registry carries authorized_workers, the two can diverge. |
| D1 boundary impact | **REQUIRES CHANGE.** WorkerIdentity gains `authorized_businesses` field → D1Persistence schema must store it. |
| D3 impact | **NONE.** Epoch authority unchanged. |
| Persistence impact | **REQUIRES D1 SCHEMA CHANGE.** New column in workers table. |
| Security strength | **LOW-MODERATE.** Worker self-declares authorization at registration — this is untrustworthy (I10, I17). A malicious worker could claim authorization for any business. |
| Same-tenant isolation | **YES** if enforced server-side, but relies on worker self-reporting, which is weak. |
| Operational complexity | **HIGH.** Requires contract change, D1 schema migration, registration protocol change. |
| Compatibility with frozen contracts | **VIOLATES.** WorkerIdentity is a frozen contract. Modifying it violates the frozen contract boundary. |

### Option C: Separate Business Authorization authority

| Dimension | Assessment |
|-----------|-----------|
| Authority duplication | **NONE.** Single new authority. |
| D1 boundary impact | **NEW TABLE.** Would require a new authorization table (not modifying D1's workers table, but adding a new store). |
| D3 impact | **NONE.** |
| Persistence impact | **NEW PERSISTENCE.** A new `business_authorization` table/store. |
| Security strength | **HIGH.** Dedicated authorization layer, clear separation. |
| Same-tenant isolation | **YES.** |
| Operational complexity | **MODERATE.** New module, new schema, new enforcement. More complex than Option A. |
| Compatibility with frozen contracts | **FULL.** No changes to frozen contracts. |

### Option D: Tenant-only authorization (current model)

| Dimension | Assessment |
|-----------|-----------|
| Authority duplication | **NONE.** Current model is simple. |
| D1 boundary impact | **NONE.** |
| D3 impact | **NONE.** |
| Persistence impact | **NONE.** |
| Security strength | **INSUFFICIENT.** Same-tenant businesses are NOT isolated. A worker with `tenant_scope = ("tenant_a",)` can serve both Business A and Business B under tenant_a. |
| Same-tenant isolation | **NO.** This is the defect D4 must resolve. |
| Operational complexity | **LOW.** But architecturally broken. |
| Compatibility with frozen contracts | **FULL.** |

### Option Evaluation Summary

| Option | Same-Tenant Isolation | Frozen Contracts | D1 Impact | Complexity | Security |
|--------|-----------------------|------------------|-----------|------------|----------|
| **A: Business Registry** | **YES** | **FULL** | **NONE** | **LOW** | **HIGH** |

## 4. CRITICAL QUESTION RESOLUTION

> Can D4 satisfy true same-tenant business isolation without modifying WorkerIdentity / D1 persistence?

**YES.**

**Exact authority flow:**

1. Business definition in Business Registry (businesses.json) declares:
   - `tenant_scope: "tenant_a"` — which tenant this business belongs to
   - `authorized_workers: ["worker_alpha", "worker_beta"]` — which workers may serve this business

2. At dispatch time (ExecutionEngine._worker → WorkerMatcher):
   - Resolve `business_id` from task input `_business_id`
   - Look up business definition from Business Registry → get `tenant_scope` and `authorized_workers`
   - Create `DispatchConstraints(tenant_scope=business.tenant_scope)`
   - WorkerMatcher filters candidates by `tenant_scope ∈ worker.identity.tenant_scope` (existing mechanism)
   - **NEW CHECK (in WorkerMatcher or pre-dispatch):** verify `worker_id ∈ business.authorized_workers`
   - If the worker is not on the authorized list, the candidate is rejected

3. This check is performed BEFORE tool invocation, in the same dispatch path.

**Why this does NOT require WorkerIdentity or D1 changes:**
- The authorization data lives in the Business Registry (businesses.json)
- The enforcement happens in WorkerMatcher (which is NOT a frozen contract)
- DispatchConstraints (which is NOT a frozen contract) gains a `business_id` field
- WorkerIdentity remains immutable — it carries `tenant_scope` (the worker's platform-level tenant), not business-level authorization
- D1Persistence stores only worker identity and runtime state — business authorization is outside its scope

## 7. CURRENT ARCHITECTURE SUFFICIENCY

**D4 ARCHITECTURE: NOT READY**

**Justification:**

The current implementation provides tenant_scope isolation through an accidental mechanism: `business_id` is used directly as the `tenant_scope` filter value (execution_engine.py:473). This works ONLY because:
1. The system does not model shared tenants (no `tenant_scope` on business definitions)
2. Each business_id is treated as an independent scope value
3. No explicit worker → business authorization exists

This is NOT true business-level authorization because:
1. There is no `business_id → tenant_scope` mapping (businesses.json has no `tenant_scope` field)
2. There is no `worker → authorized_businesses` relationship
3. If the architecture evolves to support `Tenant A → {Business A, Business B}`, the current system CANNOT isolate businesses within the same tenant
4. The system does not distinguish between "this worker serves this tenant" and "this worker is authorized for this specific business"

**The minimum architectural change required:**

1. Add `tenant_scope` field to business definitions in businesses.json
2. Add `authorized_workers` field to business definitions
3. Add `business_id` field to DispatchConstraints (non-frozen contract)
4. Add business authorization check to WorkerMatcher (non-frozen contract)
5. Update ExecutionEngine._worker to resolve business → tenant_scope from Business Registry (instead of using business_id as tenant_scope)

No frozen contracts are modified. No D1 schema is modified. No WorkerIdentity is modified.
